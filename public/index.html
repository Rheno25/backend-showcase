What the process actually does

          
Request path

        

        

          
          
          
          
        

      

      

        

          
One Node process owns the HTTP server, an in-memory LRU inventory cache, the token bucket, the payment circuit, and a SQLite file. There is no separate Kafka or Redis in this repo. The boundaries are real function boundaries, so each one can be split out later without changing the HTTP contract.

Read path
GET /v2/inventory/:sku checks a 5 second LRU cache, otherwise reads SQLite and stores the row. A successful order deletes that key.

            
Write path
POST /v2/orders takes a write transaction, checks the version columns, and stores the idempotency key in the same commit as the order.

          

        

        

          
A new order is validated, checked for an existing idempotency key, then charged against the token bucket. Replays of a committed key skip the bucket so a client retry still receives the original order.

          
BEGIN IMMEDIATE
-- refuse a key that was stored with a different body
-- UPDATE inventory SET available = available - ?, version = version + 1
--   WHERE sku = ? AND version = ? AND available >= ?
-- UPDATE accounts SET balance_cents = balance_cents - ?, version = version + 1
--   WHERE id = ? AND version = ? AND balance_cents >= ?
-- INSERT order + idempotency key
COMMIT

        

        

          
The version predicate is optimistic locking. If another writer committed first, changes comes back as 0 and the API returns 409 instead of overwriting their update. SQLite serializes writers; the version check is what you would keep if the row moved to Postgres.

          
UPDATE inventory
SET available = available - :qty,
    reserved = reserved + :qty,
    version = version + 1
WHERE sku = :sku
  AND version = :expected
  AND available >= :qty

        

        

          
POST /v2/payments calls a gateway object through a circuit breaker. Mark the gateway down from the playground. After 4 failures in the window, the next call returns 503 and does not touch the gateway. Resetting the circuit lets a healthy gateway capture the reserved order.

          

            
Closed
Calls reach the gateway. Failures are counted.

            
Open
Calls fail fast with CIRCUIT_BREAKER_OPEN.

            
Half-open
After the cooldown, one trial call decides whether to close.
